D1 · Agentic architecture & orchestration

27% · ~16 of 60 questions
D1 in five lines
  1. Loop on stop_reason, never on text.
  2. Subagents see nothing you do not put in their prompt.
  3. All traffic goes through the coordinator.
  4. Must-always rules go in hooks or gates, not the prompt.
  5. Big job: split it. Predictable → fixed chain. Open-ended → adaptive plan.
1.1

Agentic loop

Send messages→stop_reason?
tool_useRun the tool → append tool_result to messages → send again (loop) end_turnStop. The task is done.
Pick
  • Continue on tool_use, stop on end_turn
  • Append every tool result to history
  • Let Claude choose the next tool (model-driven)
Reject
  • Parse text like "I'm done" to stop
  • Iteration cap as the main stop rule
  • "Reply has text, so it is finished"
  • Hard-coded tool sequence for an open task
1.2

Coordinator and subagents

you missed
Search agentAnalysis agent
Coordinator
Synthesis agentHuman / user
Pick
  • Hub-and-spoke: every message goes through the coordinator (observability, one error policy)
  • Coordinator picks which subagents to run based on how complex the query is
  • Split scope into distinct subtopics or source types (no duplicate work)
  • Loop: check the synthesis for gaps → re-delegate targeted queries → re-synthesize
Reject
  • Always run the full pipeline
  • Blame the downstream agents when the coordinator's split was too narrow
  • Subagents passing work to each other directly

Need agents that message each other and share a task list? That is Claude Code agent teams, not subagents. A subagent cut off by an API error returns its partial text plus a cut-off note.

1.3

Starting subagents and passing context

Pick
  • Spawn with the Task tool. The coordinator's allowedTools must include "Task"
  • Put complete prior findings in the subagent's prompt
  • Structured format that keeps content apart from metadata (URL, document, page) so citations survive
  • Parallel = several Task calls in one response
  • Give goals and quality criteria, not step-by-step orders
Reject
  • "The subagent can see the parent's history" (it cannot)
  • Shared memory between calls
  • Parallel work spread across separate turns
  • Long procedural scripts for each subagent

AgentDefinition = description + system prompt + tool restrictions for each subagent type.

1.4

Enforcement and handoff

Pick
  • Code gate: block process_refund until get_customer returned a verified ID
  • Handoff to a human = structured summary: customer ID, root cause, amount, recommended action (the human has no transcript)
  • Request with several issues: split them, investigate in parallel, give one unified answer
Reject
  • Prompt-only ordering for compliance (failure rate is never 0)
  • Few-shot examples as the fix for a must-always rule
  • Pasting the raw transcript to the human

D2 · Tool design & MCP integration

18% · ~11 of 60 questions
D2 in five lines
  1. The tool description is how Claude picks a tool. Fix bad picks there first.
  2. Errors are structured: category, retryable, plain message.
  3. Each agent gets only its role's tools (4–5, not 18).
  4. any = some tool. tool = that tool. auto = maybe none.
  5. Team MCP → .mcp.json with ${ENV}. Personal → ~/.claude.json.
2.1

Tool descriptions

Pick
  • Description states purpose, input format, example queries, edge cases, and when to use it instead of a similar tool
  • Rename overlapping tools (analyze_content → extract_web_results)
  • Split a generic tool into specific ones (extract_data_points, summarize_content, verify_claim_against_source)
  • Check the system prompt for keywords that pull Claude to the wrong tool
Reject
  • One-line descriptions
  • Two tools with near-identical descriptions
  • Routing classifier or fine-tuning as the first fix (over-engineered)
2.2

Structured MCP errors

Return isError: true + errorCategory + isRetryable + a readable description.

CategoryExampleRetry?Agent does
TransientTimeout, service downYesRetry locally in the subagent
ValidationBad inputNot as-isFix the input
BusinessPolicy violationNoExplain to the customer (friendly message)
PermissionAccess deniedNoEscalate
Pick
  • Subagent retries transient errors itself; sends only unresolved errors up, with partial results and what it tried
  • Empty result = a successful query with no matches, not an error
Reject
  • Generic "Operation failed"
  • Hiding errors or returning them as empty success
  • Ending the whole workflow on one failure

MCP servers in Claude Code

Pick
  • Tools from all servers load at connect time and are all available at once
  • MCP resources expose catalogs (issue list, doc tree, DB schema) so the agent explores less
